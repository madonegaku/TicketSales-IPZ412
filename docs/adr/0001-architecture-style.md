## Контекст

Система продає квитки на місця в залі, тому головна вимога – жодного подвійного продажу ([С-03](../quality-scenarios.md#с-03-надійність-цілісність-даних)) і жодного втраченого оплаченого замовлення ([С-04](../quality-scenarios.md#с-04-надійність-відмовостійкість)). На старті продажу навантаження різко зростає (С-01, С-02). Частина операцій повільна або залежить від зовнішніх сервісів: надсилання листів, генерація QR-квитків, звірка платежів з LiqPay, фіскалізація. Команда складається з трьох осіб без досвіду роботи з вебфреймворками та базами даних, строк – один семестр (С-09).

## Розглянуті варіанти

1. **Модульний моноліт** – найпростіший, ACID-транзакції в одній БД; повільні операції блокують запити, немає повторних спроб при збоях шлюзу. Оцінка **4,05**.
2. **Модульний моноліт з фоновими обробниками** – ACID-транзакції плюс черга задач для повільних і ненадійних операцій. Оцінка **4,30**.
3. **Три сервіси** – незалежне масштабування, але розподілені транзакції та трудомісткість, нереалістична для команди. Оцінка **2,35**.

Детальне порівняння за критеріями К1–К4 – у [architecture-comparison.md](../architecture-comparison.md).

## Рішення

Обрано **модульний моноліт з фоновими обробниками**, бо він має найвищу зважену оцінку і найкраще виконує критерій К2 (цілісність і надійність) при прийнятній трудомісткості (К3).

Модулі системи:

| Модуль | Відповідальність |
| --- | --- |
| `catalog` | Заходи, майданчики, схеми залів |
| `booking` | Резервування |
| `payments` | Оплати та повернення |
| `tickets` | Квитки та валідація |
| `notifications` | Листи |
| `reports` | Звіти |

Модулі взаємодіють лише через свої публічні функції, без прямого доступу до таблиць один одного.

## Наслідки

**Позитивні:**

- Одна база даних дає транзакційну гарантію відсутності подвійного продажу.
- Збої зовнішніх сервісів не ламають оформлення замовлення: задачі повторюються у фоні.
- Один репозиторій і одне розгортання, посильні для команди з трьох осіб.

**Негативні:**

- Додається інфраструктура: брокер черги та процес-обробник.
- Листи й квитки надходять не миттєво, а із затримкою в кілька секунд.
- Фонові задачі мають бути ідемпотентними, що ускладнює код і налагодження.

**Технічний борг:** одна база даних – єдина точка відмови; масштабування переважно вертикальне. Якщо навантаження перевищить можливості одного сервера, модуль оплат буде кандидатом на виділення в окремий сервіс (новий ADR).
