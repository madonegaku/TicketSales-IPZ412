## Контекст

Усі учасники команди володіють мовою Python, але не працювали з вебфреймворками та базами даних. Стек має реалізувати [ADR-001](0001-architecture-style.md): транзакційну БД з блокуванням рядків (С-03), чергу фонових задач (С-04), захист від ботів (С-06) і просте розгортання (С-09). Обраний стек має бути посильним для освоєння за 2–3 тижні.

## Розглянуті варіанти

1. **Django + PostgreSQL + Celery + Redis.** Фреймворк «з батарейками»: ORM, міграції, автентифікація, адмін-панель, шаблони, захист від CSRF уже вбудовані. Велика документація з покроковим навчальним прикладом.
2. **FastAPI + SQLAlchemy + PostgreSQL + Celery + Redis.** Висока швидкодія та асинхронність, але ORM, міграції, автентифікацію та адмін-панель доводиться збирати й налаштовувати окремо – більше роботи для новачків.
3. **Flask + SQLite.** Найпростіший старт, але SQLite погано витримує одночасні записи й не має блокування окремих рядків, тому не виконує С-03 під навантаженням.

Варіанти оцінено за чотирма критеріями з однаковою вагою: поріг входу для команди без досвіду (К3), наявність вбудованих засобів (К3, С-08), цілісність даних при одночасних резервуваннях (С-03) і підтримка фонових задач (С-04). Оцінка 1–5, де 5 – найкраще.

| Критерій | Django + PostgreSQL + Celery | FastAPI + SQLAlchemy + PostgreSQL + Celery | Flask + SQLite |
| --- | --- | --- | --- |
| Поріг входу для команди | **4** – один фреймворк, покроковий офіційний навчальний приклад | **3** – ORM, міграції й автентифікацію треба обирати та поєднувати самостійно | **5** – мінімум понять для старту |
| Вбудовані засоби (ORM, міграції, автентифікація, адмін-панель) | **5** – усе є «з коробки» | **2** – окремі бібліотеки для кожної функції | **2** – окремі розширення, адмін-панелі немає |
| Цілісність при одночасних резервуваннях (С-03) | **5** – транзакції та блокування рядків PostgreSQL | **5** – та сама СУБД PostgreSQL | **1** – SQLite блокує всю базу під час запису, блокування рядків немає |
| Фонові задачі та повторні спроби (С-04) | **5** – Celery + Redis | **5** – Celery + Redis | **2** – черга задач цим варіантом не передбачена |
| **Сума балів** | **19** | **15** | **10** |

## Рішення

Обрано **варіант 1**: він набрав найбільшу суму балів (19 із 20) і єдиний поєднує прийнятний поріг входу для команди з вбудованими засобами та гарантією цілісності даних (С-03).

| Компонент | Технологія | Навіщо |
| --- | --- | --- |
| Мова | Python 3.12 | Усі учасники володіють мовою |
| Вебфреймворк | Django 5 (шаблони для інтерфейсу, Django REST Framework для API сканера контролера) | Вбудовані ORM, міграції, автентифікація, адмін-панель для організаторів і адміністраторів |
| База даних | PostgreSQL 16 | ACID-транзакції, `SELECT … FOR UPDATE` та унікальні обмеження проти подвійного продажу (С-03) |
| Черга задач | Celery 5 + Celery Beat | Листи, генерація квитків, звірка платежів, звільнення прострочених резервувань (С-04) |
| Брокер і кеш | Redis 7 | Брокер Celery, кеш схем залів (С-01), обмеження частоти запитів (С-06) |
| Розгортання | Docker Compose | Запуск усієї системи однією командою (С-09) |
| Тестування | pytest, pytest-django, Locust | Модульні тести (С-08), навантажувальні тести (С-01 – С-03) |

## Наслідки

**Позитивні:**

- Більшість типових задач (вхід, ролі, адмін-панель, міграції) закрито вбудованими засобами Django.
- PostgreSQL гарантує цілісність місць на рівні бази даних.
- Docker Compose дає однакове середовище в усіх учасників.

**Негативні:**

- Команді потрібно 2–3 тижні на освоєння Django, ORM і SQL.
- Django за замовчуванням синхронний; масштабування – через кількість процесів веб-сервера.
- Celery складніше налагоджувати, ніж звичайний код.

**Технічний борг:** інтерфейс на серверних шаблонах; за потреби мобільного застосунку чи SPA знадобиться повноцінний REST API (новий ADR).
