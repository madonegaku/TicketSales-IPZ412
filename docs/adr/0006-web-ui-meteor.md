## Контекст

Після ЛР 5 система має три сервіси, але людей у ній немає: усі покупки йдуть від одного демонстраційного покупця, сторінка контролера `/validate/` відкрита всім, а організатор і адміністратор (ролі з ЛР 1) не мають інтерфейсу. У матриці володіння ЛР 5 покупець не має власника всередині системи, ліміт С-06 «≤ 6 квитків на акаунт» не може працювати без акаунтів. Команда вирішила зробити сучасний інтерфейс на Meteor із чотирма ролями, зберігши сторінки Django для демонстрацій ЛР 2–5.

## Розглянуті варіанти

1. **Ролі й вхід у кожному сервісі Django** (django.contrib.auth у sales і tickets). Два окремі набори користувачів або спільна таблиця користувачів – друге порушує правило «без спільної бази» (табл. 3.3, 5.3).
2. **Meteor-застосунок, що звертається до сервісів із браузера.** Кожен сервіс мав би бути доступним ззовні й сам перевіряв би вхід; токени зберігалися б у браузері.
3. **Окремий сервіс web на Meteor як «бекенд для фронтенду»**: власник облікових записів і ролей (власна MongoDB), сервер Meteor викликає JSON API sales і tickets від імені користувача й передає короткий підписаний токен із його ідентифікатором і ролями; сервіси перевіряють підпис і роль.

| Критерій | Django auth у сервісах | Meteor із браузера | Meteor як BFF |
| --- | --- | --- | --- |
| Один власник облікових записів (ЛР 5) | 2 | 4 | 5 |
| Без спільної бази й синхронних ланцюгів | 2 | 4 | 4 |
| Сервіси не відкриті назовні | 4 | 1 | 5 |
| Обсяг змін у наявних сервісах (менше – краще) | 2 | 3 | 4 |
| Нові технології для команди (менше – краще) | 5 | 2 | 2 |
| **Сума балів** | **15** | **14** | **20** |

## Рішення

Обрано **варіант 3**.

- **Сервіс web** (каталог `web/`, Meteor 3, React): облікові записи (`accounts-password`) і ролі (`buyer`, `organizer`, `inspector`, `admin`) у власній MongoDB (`web-db`). Кожен користувач має `subjectId` – UUID, яким його знають інші сервіси (у домені sales це `buyer_id` / `organizer_id`). Перший адміністратор створюється під час старту зі змінних середовища.
- **Токен доступу:** сервер web на кожен виклик підписує JWT (HS256, секрет `AUTH_TOKEN_SECRET` спільний для web, sales і tickets) з полями `sub` (subjectId), `roles`, `iss = web`, `aud = ticketsales`, строком дії 5 хвилин. sales і tickets перевіряють підпис, строк і роль у шарі presentation; домен і сценарії не знають про токени.
- **JSON API** (`/api/v1/…`) у sales і tickets – нові контракти OpenAPI; сторінки Django лишаються без змін.
- **Шлюз:** Meteor – окремий порт `8090`; шлях `/api/` на порту `8080` закрито – API викликає лише web усередині мережі Docker.
- **Власність даних:** web володіє користувачами й ролями; sales – заходами (тепер із власником-організатором), резервуваннями й замовленнями; tickets – квитками. web не зберігає копій заходів чи квитків – лише запитує їх.

## Наслідки

**Позитивні:**

- Ліміт С-06 рахується для справжнього покупця; квитки й замовлення видно лише власникові; перевірка на вході – лише контролерові.
- Організатор створює заходи й бачить статистику продажу; адміністратор керує користувачами й ролями.
- Сервіси не відкриті назовні, а підробити роль без секрету неможливо.

**Негативні:**

- Новий стек (Node.js, Meteor, MongoDB) і ще два контейнери.
- Спільний секрет підпису в трьох сервісах; його зміна – узгоджене розгортання.
- web – ще одна точка відмови для людей (сторінки Django працюють і без нього).

**Технічний борг:**

- HS256 зі спільним секретом – для навчального проєкту; для експлуатації – асиметричний підпис (RS256), щоб сервіси мали лише відкритий ключ.
- Відкликання ролі набуває чинності не пізніше ніж через 5 хвилин (строк дії токена).
