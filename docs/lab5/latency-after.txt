# Додаткові вимірювання кешу схеми залу (04.11.2026)
# Основне порівняння «до і після» – latency-comparison.txt (tools/compare_cache.py),
# вимірювання до появи коду кешу – latency-before.txt.

# 1. Сценарій GetHallLayout усередині контейнера sales (без HTTP, шлюзу й шаблону),
#    1000 викликів після 50 прогрівальних, двічі поспіль
GetHallLayout без кешу (PostgreSQL): p50 1.07 мс, p95 1.69 мс | повтор: p50 1.14 мс, p95 1.93 мс
GetHallLayout з кешем (Redis):       p50 0.28 мс, p95 0.65 мс | повтор: p50 0.26 мс, p95 0.38 мс

# 2. З чого складається час сторінки без кешу (1 клієнт)
запит GetHallLayout до PostgreSQL     ≈ 1,1 мс
рендеринг шаблону hall.html           ≈ 2,3 мс (p50 2.26 мс, p95 4.34 мс)
HTTP, шлюз nginx, сервер розробки      ≈ 3,3 мс (решта до p50 сторінки 6,6 мс)
Кешується лише результат запиту: HTML кешувати не можна – у формі CSRF-токен кожного відвідувача.

# 3. Redis зупинено (docker compose stop redis), 1 клієнт
без запобіжника: одна сторінка 7,8 с – кожне звернення до кешу чекає DNS зупиненого Redis
                 («Name or service not known»), тайм-аут з'єднання 0,2 с цей етап не обмежує
із запобіжником: 200 запитів, p50 6.6 мс, p95 7.6 мс – як без кешу; після docker compose start redis
                 журнал: «Redis знову доступний: записи кешу схем залу видалено, кеш увімкнено.»

# 4. Чому спершу отримали суперечливі результати
Без перезапуску контейнерів між серіями час відповіді на Docker Desktop для Windows зростав від
серії до серії незалежно від кешу:
  з кешем, 10 клієнтів, серії поспіль: p50 51.8 → 155.1 → 199.6 мс
  без кешу, 10 клієнтів, серії поспіль: p50 70.8 → 86.8 → 97.8 мс
Тому порівняння виконано скриптом tools/compare_cache.py: перед кожною серією sales і шлюз
перезапускаються, режими чергуються (без, з, без, з). Повторні серії кожного режиму збігаються
в межах 1 мс для 1 клієнта й 3 мс для 10 клієнтів.
