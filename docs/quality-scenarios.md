# Сценарії атрибутів якості (ЛР 1)

> Розділ 5 звіту. Інженер з якості: Пащенко О.А.

Сценарії записано за шестичастинною формою (джерело, стимул, артефакт, середовище, реакція, міра реакції). Сформульовано 9 сценаріїв, що охоплюють чотири атрибути: продуктивність (С-01, С-02), надійність (С-03, С-04), безпеку (С-05 – С-07) і підтримуваність (С-08, С-09). Кожна міра реакції перевіряється навантажувальним, інтеграційним або ручним тестом.

## Зведена таблиця

| № | Атрибут | Стимул | Міра реакції |
| --- | --- | --- | --- |
| [С-01](#с-01-продуктивність-перегляд-схеми-залу) | Продуктивність | Покупці відкривають схему залу | p95 ≤ 500 мс при 300 запитах/с |
| [С-02](#с-02-продуктивність-резервування) | Продуктивність | Покупець резервує 1–6 місць | p95 ≤ 1 с; ≥ 100 резервувань/с |
| [С-03](#с-03-надійність-цілісність-даних) | Надійність | Одночасне резервування того самого місця | 0 подвійних продажів на 10 000 спроб |
| [С-04](#с-04-надійність-відмовостійкість) | Надійність | Платіжний шлюз недоступний | 0 втрачених оплачених замовлень |
| [С-05](#с-05-безпека-підроблене-підтвердження-оплати) | Безпека | Підроблений callback оплати | 100 % невалідних підписів відхилено |
| [С-06](#с-06-безпека-захист-від-ботів) | Безпека | Масові запити бота | ≤ 6 квитків на акаунт; ≤ 10 запитів/хв з IP |
| [С-07](#с-07-безпека-повторне-використання-квитка) | Безпека | Повторне сканування QR-коду | 100 % повторів відхилено; ≤ 1 с |
| [С-08](#с-08-підтримуваність-внесення-змін) | Підтримуваність | Новий спосіб оплати | ≤ 1 модуль; ≤ 2 людино-дні; покриття ≥ 80 % |
| [С-09](#с-09-підтримуваність-розгортання) | Підтримуваність | Розгортання на чистому комп'ютері | ≤ 30 хв до робочої системи |

## С-01: продуктивність (перегляд схеми залу)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Анонімні та зареєстровані покупці |
| Стимул | Відкривають сторінку заходу зі схемою залу |
| Артефакт | Модуль каталогу та схеми залу |
| Середовище | Старт продажу популярного заходу, 5 000 одночасних сесій |
| Реакція | Повертає схему залу з актуальним статусом кожного місця |
| **Міра реакції** | **p95 часу відповіді ≤ 500 мс при 300 запитах/с** |

## С-02: продуктивність (резервування)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Зареєстрований покупець |
| Стимул | Натискає «Забронювати» для 1–6 місць |
| Артефакт | Модуль резервування |
| Середовище | Пікове навантаження, 5 000 одночасних сесій |
| Реакція | Створює резервування на 15 хв і переводить до оплати |
| **Міра реакції** | **p95 ≤ 1 с; пропускна здатність ≥ 100 резервувань/с** |

## С-03: надійність (цілісність даних)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Два й більше покупців |
| Стимул | Одночасно резервують те саме місце |
| Артефакт | Модуль резервування, база даних |
| Середовище | Пікове навантаження |
| Реакція | Успішним стає лише одне резервування, решта отримують повідомлення «місце зайняте» |
| **Міра реакції** | **0 подвійних продажів у навантажувальному тесті з 10 000 конкурентних спроб** |

## С-04: надійність (відмовостійкість)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Платіжний шлюз LiqPay |
| Стимул | Недоступний або не надсилає підтвердження оплати |
| Артефакт | Модуль оплат, фонові обробники |
| Середовище | Шлюз недоступний до 30 хв |
| Реакція | Замовлення лишається в статусі «очікує оплати», фонова задача кожні 2 хв перевіряє статус платежу |
| **Міра реакції** | **0 втрачених оплачених замовлень; 100 % оплачених квитків надіслано ≤ 10 хв після відновлення шлюзу** |

## С-05: безпека (підроблене підтвердження оплати)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Зловмисник |
| Стимул | Надсилає підроблене підтвердження оплати на адресу callback |
| Артефакт | Модуль оплат |
| Середовище | Штатна робота |
| Реакція | Перевіряє підпис запиту, відхиляє його, записує подію в журнал безпеки |
| **Міра реакції** | **100 % запитів з невалідним підписом відхилено; 0 квитків видано без підтвердженої оплати** |

## С-06: безпека (захист від ботів)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Бот перекупника |
| Стимул | Надсилає масові запити на резервування |
| Артефакт | Модуль резервування, захист від ботів |
| Середовище | Старт продажу |
| Реакція | Обмежує частоту запитів, вимагає reCAPTCHA, обмежує кількість квитків |
| **Міра реакції** | **≤ 6 квитків на захід на акаунт; ≤ 10 запитів резервування на хв з одного IP; 100 % перевищень заблоковано** |

## С-07: безпека (повторне використання квитка)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Відвідувач з копією квитка |
| Стимул | Пред'являє вже використаний QR-код |
| Артефакт | Модуль валідації квитків |
| Середовище | Захід триває, на вході 2 000 глядачів за 1 год |
| Реакція | Відмовляє в проході, показує час першого сканування |
| **Міра реакції** | **100 % повторних сканувань відхилено; відповідь сканеру ≤ 1 с** |

## С-08: підтримуваність (внесення змін)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Розробник команди |
| Стимул | Додає новий спосіб оплати або новий тип знижки |
| Артефакт | Модуль оплат |
| Середовище | Етап розробки |
| Реакція | Зміну внесено без правок в інших модулях, усі тести проходять |
| **Міра реакції** | **Змінено ≤ 1 модуль; ≤ 2 людино-дні; покриття нового коду тестами ≥ 80 %** |

## С-09: підтримуваність (розгортання)

| Частина сценарію | Значення |
| --- | --- |
| Джерело стимулу | Новий учасник команди |
| Стимул | Розгортає систему на своєму комп'ютері |
| Артефакт | Уся система |
| Середовище | Чистий комп'ютер з Docker |
| Реакція | Система запускається однією командою з тестовими даними |
| **Міра реакції** | **≤ 30 хв від клонування репозиторію до робочої системи** |
